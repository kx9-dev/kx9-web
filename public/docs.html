KX-9 · Mainnet integration guide

Connect, configure and operate KX-9

The Command app uses a same-origin Core API, verified Robinhood mainnet reads and wallet-owned settings. Missing services stay unavailable; no demonstration vaults, prices, trades or history are generated.

Updated 29 Oct 2026 · Mainnet chain ID 4663 · Landing: kx9.tech · App: app.kx9.tech. Website publication, RPC connectivity and trading readiness are separate.

Wallet and sign-in flow

  1. Open KX-9 Command and connect an EVM wallet.
  2. Switch to Robinhood mainnet (4663). App reads use the private backend; wallet transactions use the wallet's own network provider. Network setup offers Robinhood's public RPC address, never the private server URL. The app's read-only proxy intentionally cannot broadcast transactions.
  3. Select Sign in. The server creates an exact, domain-bound message with a five-minute, single-use challenge.
  4. Review and sign the message in your wallet. Signing in does not send a transaction or cost gas.
  5. The Core verifies the signature and discovers units owned by that wallet through the configured factory. An empty unit list means no verified unit was found—not that a new vault was created.
  6. You can save protocol settings before commissioning. Saved settings do not start trades.

Sessions expire after 24 hours. Settings and records are stored in PostgreSQL, not the deployment filesystem. Sign out revokes the current session.

KX-9 is not affiliated with NVIDIA Corporation or Robinhood Markets. Stock-token availability, redemption and legal rights depend on the actual issuer and jurisdiction.

All protocols start off. Editing is local until Save protocols succeeds. A selected strategy is not evidence that execution is active. Account defaults are applied to newly discovered units; each existing unit has separately saved settings.

Decision, risk and execution flow

  1. The rule-based Analyst considers saved protocols and verified oracle observations.
  2. The Risk Officer checks unit class, mode, both asset permissions, trade limit, daily usage, cooldown, input balance, feed freshness, sequencer uptime and a real router quote.
  3. A failed check records a veto; no transaction is sent.
  4. In Supervised mode, the operator signs approveProposal on the Shield. The Core checks the successful transaction's sender, destination, proposal ID, amount, expiry and unused on-chain approval.
  5. An explicitly enabled executor may submit through the configured Shield and router. Submitted is not Confirmed. Confirmation is reconciled from the mainnet receipt.
  6. In Autonomous mode, a verified Mk II or Mk III holding and all risk checks are still required. Standby blocks new submissions; a transaction already broadcast cannot be cancelled by changing a label in the app.

Missing executor settings do not fall back to simulated fills. Optional AI narration can only explain a fixed proposal; it cannot choose trade amounts, waive risk checks or sign transactions.

Shield and mode changes

Limits are read from the selected on-chain vault. The app stages an edit, shows differences, and asks the wallet to sign each required contract transaction. Changes are confirmed only after transaction verification and a fresh read-back of the values. No local-save branch substitutes for a chain transaction.

To commission a unit, the factory must be configured and the operator must confirm the deployment transaction in their wallet. KX9 token deployment remains the owner's responsibility. The supplied Shield sources are unchanged; tests are not an audit.

Historical testing without invented prices

Sign in, save your settings, then choose Historical test. Upload a CSV with date,close columns, 2–366 increasing UTC daily dates and positive closing prices. Physical AI forces NVDA as the asset. The file is parsed in the browser; only the numeric observations are sent for calculation and they are not stored.

Black Box, Passport and live updates

The Black Box records actual proposal, veto, approval and transaction events. Search and role filters apply to the current wallet's records. Times use UTC. Records have SHA-256 integrity hashes; these are not independent validator signatures or ERC-8004 attestations.

The Passport shows verified operator, unit and Shield identity. Reputation scores, uptime and breach counts remain unavailable unless independently measured; no placeholder score is presented. The Core streams authenticated server-sent events, with six-second state polling as a fallback and refresh on window focus.

In Protocols, Export my data downloads your off-chain settings and records. Delete off-chain data requires explicit confirmation and revokes sessions. It does not withdraw funds, destroy a vault, erase blockchain history or revoke an executor's on-chain authority. Set the vault to Standby on-chain before deleting records if you need activity to stop.

Configuration and readiness

Configure credentials only through workspace Secrets. Never put a private key or private RPC address into HTML or a public configuration file.

Publishing serves the website and API; it does not deploy contracts or fund an executor. The public /api/v1/config response contains contract addresses and capability flags only, never provider credentials or private keys.

API reference

All Core routes use /api/v1. Sign-in creates an HttpOnly secure cookie; in-memory bearer authentication is supported for embedded browsers. State-changing requests must be JSON and same-origin. Tokens must never be placed in stream URLs. Errors return {"error":{"code":"…","message":"…"}}. Owner-scoped routes reject unauthenticated access.
